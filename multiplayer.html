How the multiplayer works

A primer on the realtime architecture behind this project, the infrastructure you need to keep it alive, and the realtime-game concepts worth knowing.

Contents 1. Big picture 2. The message flow, step by step 3. Wire protocol 4. Infrastructure to keep running 5. Capacity & scaling 6. Realtime concepts to know 7. Security & cheating 8. Production checklist

1. Big picture

This is an authoritative-relay server. There is one Node.js process that every player connects to over a persistent WebSocket. The server holds the canonical state of who is in the world, where they are, and what they have drawn — and rebroadcasts everyone's updates to everyone else.

Three common multiplayer shapes you should know:

ShapeWhat it isTrade-off
Peer-to-peerClients talk to each other directly (e.g. WebRTC)No server cost. Hard with NATs, hard to keep state consistent, every client trusts every other client.
Authoritative relay (this)Server forwards messages and holds state, but doesn't simulate physics.Cheap, simple, works for casual presence apps. Clients can still cheat their own position.
Authoritative simulatorServer actually runs the physics/game logic; clients just send inputs.Cheat-resistant, used in competitive games. Much more CPU and code.

Doodler is the middle one. The server doesn't care whether your "movement" obeys physics — it just rebroadcasts what you say. (We do clamp movement deltas to prevent obvious teleport griefing, but that's the extent of validation.)

2. The message flow, step by step

Player A (browser) Server (Node) Player B (browser) ─────────────────── ──────────────── ─────────────────── │ │ │ │ open WS ────────────────▶│ │ │◀──────── { t:"welcome", id } │ │◀──────── { t:"snapshot", players:[ B... ] } │ │ │ │ │ { t:"join", drawing } ───▶│ │ │ │ { t:"join", id:A, ... } ─▶│ │ │ │ │ { t:"move", x,z,rotY } ──▶│ (15 Hz) │ │ │ { t:"update", id:A } ────▶│ │ │ │ │ { t:"chat", text } ──────▶│ │ │◀──── { t:"chat", id:A, text } (echo to sender too) │ │ │ { t:"chat", id:A, text }─▶│ │ │ │ │ close WS ───────────────▶│ │ │ │ { t:"leave", id:A } ─────▶│

What each step is doing

  1. 1WebSocket handshake. A plain HTTP request that gets "upgraded" into a persistent bidirectional connection. Lives until either side closes.
  2. 2Welcome + snapshot. The server assigns a UUID and sends the new client the current world state. This is your initial render of everyone already in the room.
  3. 3Join. The new client sends its drawing (as a PNG data URL) once. The server stores it and tells every other client "this person just joined, here's what they look like."
  4. 4Move updates. ~15 times per second, the client sends its current position. The server forwards to everyone else. Other clients interpolate between updates so motion looks smooth.
  5. 5Chat. Sent once per message. The server broadcasts to everyone including the sender so the sender's own bubble appears via the same code path as everyone else's.
  6. 6Leave. When the socket closes (tab closed, network drop, server-side timeout), the server tells everyone else to remove that player.

3. Wire protocol

Every message is JSON with a one-letter type field t. Keeping it short matters: at 15 Hz move updates with N players, every byte of overhead compounds.

Client → Server

{ "t": "join",  "drawing": "data:image/png;base64,..." }
{ "t": "move",  "x": 1.2, "z": -3.4, "rotY": 0.7 }
{ "t": "chat",  "text": "hello" }

Server → Client

{ "t": "welcome",  "id": "uuid" }
{ "t": "snapshot", "players": [ { "id", "drawing", "x", "z", "rotY" }, ... ] }
{ "t": "join",     "id", "drawing", "x", "z", "rotY" }
{ "t": "update",   "id", "x", "z", "rotY" }
{ "t": "chat",     "id", "text" }
{ "t": "leave",    "id" }
Watch out: The drawing is sent as a base64 PNG (~10–50 KB per player). For 10 players this is fine; for 100+ you'd want to switch to binary frames or upload to a CDN and send only a URL.

4. Infrastructure to keep running

At a minimum, to keep a server alive 24/7 you need exactly one thing: a Linux box with Node.js that stays online. Everything else is hardening.

The minimal stack

A small VPS

$5–10/month on Hetzner, DigitalOcean, Fly, Railway, Render, etc. 1 vCPU and 512 MB RAM is enough for ~100 concurrent players.

Node.js

v18 or newer. The server is one file (server.js) that listens on TCP port 8080.

A process manager

pm2 or a systemd unit. If the Node process crashes, you want it restarted within a second.

A reverse proxy (for production)

nginx or Caddy in front of Node. Terminates TLS, serves the static client, upgrades /ws to WebSocket and forwards to Node.

The client is static

After npm run build, the client is just HTML/JS/CSS. Host it on any static CDN (Cloudflare Pages, Netlify, S3, GitHub Pages, your nginx). The static client connects back to your Node server via WebSocket.

TLS / wss

If your site is served over HTTPS, browsers require the WebSocket also be encrypted (wss://, not ws://). Easiest path: put Caddy in front, point it at your domain, it gets a free Let's Encrypt cert and proxies WebSocket to your Node server automatically.

# Caddyfile — full TLS + WS proxy in 4 lines
doodler.example.com {
  reverse_proxy /ws ws://localhost:8080
  root * /var/www/doodler
  file_server
}

What you do NOT need (yet)

  • A database. All state lives in server RAM. If the server restarts, everyone's drawings are gone and they redraw on rejoin. That's fine for a casual room.
  • Redis or a message queue. Only needed if you scale past one server (see §5).
  • A CDN for the WebSocket. CDNs cache HTTP; WebSocket traffic should hit your origin directly.

5. Capacity & scaling

What "max player count" actually means

There is no single number. The ceiling is whichever of these you hit first: CPU (JSON serialization), bandwidth (each player's updates fan out to everyone), memory (small — drawings dominate), or file descriptors (each WS connection is one).

Back-of-envelope for this server

Bandwidth grows as O(N²): each of N players sends ~15 updates/sec, and each update is forwarded to N−1 other players. Per-update JSON is ~80 bytes.

PlayersOutbound msgs/secOutbound bandwidthStatus
10~1,350~110 KB/strivial
50~36,750~2.9 MB/sfine on a small VPS
100~148,500~12 MB/sstart watching CPU
200~597,000~48 MB/ssingle node is straining
500+——needs sharding (multiple rooms or area-of-interest)

Practical comfortable ceiling for this exact code on a 1-vCPU box: ~75 concurrent players in one room. With light optimization (binary frames, area-of-interest filtering so you only get updates from nearby players) you can push to a few hundred.

Scaling beyond one server

  1. Multiple rooms. The cheapest scale: spin up N independent server processes, one per "room", and route players at connect time. No shared state needed.
  2. Area of interest. Only send updates between players within ~30m of each other. Turns O(N²) into roughly O(N·k) where k is the average local crowd size.
  3. Shared state across nodes. If one room must span servers, you need a pub/sub (Redis, NATS) so move updates fan out across processes. This is a real step up in complexity — avoid until you're sure you need it.

6. Realtime concepts to know

Tick rate

How often a client sends updates. We use 15 Hz. Games like Counter-Strike use 64–128 Hz. Higher tick = lower perceived latency but more bandwidth. 15 Hz is fine for non-twitch movement.

Interpolation

If you receive a position update every 67 ms and render at 60 fps, you'd see other players "jump" between positions. So clients render slightly in the past (we delay by 120 ms) and smoothly interpolate between the two most recent received positions. This is why other people's avatars glide instead of teleport.

Latency, jitter, packet loss

  • Latency: the time for a packet to round-trip. 30 ms in-region, 150 ms cross-continent.
  • Jitter: variation in latency. A jittery connection is worse than a slow-but-steady one — interpolation hides steady latency but stutters under jitter.
  • Packet loss: on WebSocket-over-TCP, "loss" is invisible to you but shows up as head-of-line blocking — a brief freeze while TCP retransmits. UDP-based protocols (WebRTC, QUIC) handle this better but are much more work.

Client prediction (not used here)

In games where the server simulates the world, your own input is applied locally and sent to the server, and the server's authoritative answer eventually arrives and overwrites you. That's prediction + reconciliation. We don't need it because the client is authoritative over its own position.

Heartbeat / dead connection detection

TCP can keep a connection in a "half-open" state for many minutes after the other side has actually disappeared (closed laptop, dead Wi-Fi). The server pings every 30 seconds; if a client doesn't respond by the next ping, we terminate the socket. Without this, you'd see "ghost" players that never leave.

7. Security & cheating

Anyone with the browser dev tools can open a WebSocket to your server and send anything they want. Assume every client message is hostile and validate accordingly. For doodler, the realistic threats are:

  • Teleport / fly hacks. Bad client sends huge position deltas. Mitigation: server caps the delta per update (currently 10m²).
  • Spam. A client sends 1000 chat messages per second. Mitigation (todo): per-connection rate limit, e.g. token bucket of 5 messages / 10 seconds.
  • Giant drawings. A bad client uploads a 50 MB PNG. Mitigation (todo): cap the drawing size on receipt (e.g. reject > 200 KB) and validate it's actually a PNG.
  • Inappropriate content. Someone draws something objectionable. Mitigation: moderation tools (kick, IP-ban), report button, optionally a content classifier on join.
  • DoS by connection flood. Open thousands of sockets. Mitigation: per-IP connection limit at the reverse proxy.
Rule of thumb: if a number coming from the client can crash your server or affect other players, validate it on the server. Client-side validation is for UX only.

8. Production checklist

  • Reverse proxy (Caddy/nginx) with TLS, proxying /ws to Node.
  • Process manager (pm2 or systemd) with auto-restart on crash.
  • Per-IP rate limit at the proxy layer (helps with chat spam and connection floods).
  • Server-side caps: max drawing size, max chat length (currently 120 chars — already in place), max movement delta.
  • Heartbeat already enabled (30 s ping/pong) — don't disable it.
  • Log connect/disconnect events somewhere persistent so you can see usage patterns.
  • Static client uploaded to a CDN, pointing its WebSocket URL at wss://your-domain/ws.
  • Plan for restarts: when you redeploy the Node server, all current sockets drop. The client auto-reconnects? (right now it does not — worth adding before you ship.)
  • Monitoring: at minimum, an uptime ping. At best, log player count over time.
